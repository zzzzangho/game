# 08. 원작 규칙 해독 (ROM 코드 + 에뮬레이터 측정)

원칙: **원작에서 확인한 것만 규칙으로 넣는다.** 확인 방법은 두 가지다.
- 측정: `tools/gba_capture/capture.c` 로 원작을 돌리며 RAM 을 기록(`ramlog`/`autolog`)하거나, 쓰기 감시점(`watch`)으로 어느 코드가 값을 바꾸는지 잡는다.
- 해독: 그 코드 주소를 Thumb 역어셈블(capstone)해 그대로 옮긴다. 원작 코드는 최적화되지 않은 C 컴파일 결과라 한 줄씩 옮길 수 있다.

ROM·캡처·덤프는 로컬 전용이다. 아래 주소는 사용자 ROM(한글 패치판) 기준이다.

## 측정 도구
- `autolog <프레임> <누르고 있을 키> <간격> <주소> <길이> <파일>`: 화면 아래 흰 글상자가 보일 때만 A 를 눌러 대사를 넘긴다. 본화면의 A 는 **활쏘기**라서 누르지 않는다(처음 측정에서 A 를 계속 눌러 화살이 나가 결과가 오염됐었다).
- `watch <주소> <파일>`: libmgba 디버거 쓰기 감시점. 값이 바뀔 때 프레임·PC·LR·이전→새 값을 기록.
- `rtc <모드> <값>`: 카트리지 시계 덮어쓰기(원작 날짜는 시계가 아니라 프레임 기준으로 흐름을 확인하는 데 썼다).

## 확인된 규칙

### 시간
- 하루 = 사건 없는 날 **5,220~5,280 프레임**(≈ 87.9초). R 을 누르고 있으면 **780~840 프레임**(≈ ×6.48). 사건·메뉴 중에는 멈춘다.
- 카트리지 시계를 며칠 앞당겨도 날짜가 건너뛰지 않았다 → 날짜는 실시간 시계가 아니라 진행 프레임 기준.

### 난수 (ROM `0x08000614`)
`seed(0x02000000) = seed × 0x6D + 0x3FD` (32비트), 새 seed 를 돌려준다. 호출부는 `& 15`, `& 31` 처럼 아래 비트를 쓴다.

- **시작값**: 부팅 때 `0x080089DC` 가 `VCOUNT(0x04000006) × 0xAD` 를 넣는다(실기 감시: 4498 = 26×173 → 491303 → 53553048).
  그 뒤 인트로·타이틀 화면이 매 프레임 여러 번 돌리므로 새 게임 때 값은 누르는 시점에 달려 있다.
  앱(`OrigSession.BootSeed`): 주사선 값은 시각으로 고르고, 타이틀에서 돈 횟수는 타이틀에 머문 프레임 수로 대신한다(타이틀 화면 호출 횟수는 옮기지 않음).

### 인물 레코드 (가족 레코드 `0x0202C6C4 + 976×n`)
| 오프셋 | 뜻 | 근거 |
|---|---|---|
| +0x32 하위 4비트 | 성격 코드: 보통 0 · 내향적 1 · 외향적 2 | 원작 가족 만들기에서 성격만 바꿔 저장값 비교 |
| +0x48 (u16) | 지금 관심사의 날짜 수 (새 관심사 1) | 매일 +1 (`0x0802851A`) |
| +0x5A | **열중 게이지** 0~255 (새 관심사 136) | 감시점·관찰 |
| +0x5B | **하트** (0~255, 사건 효과로 변화 — "하트 상승(기본+12)" 효과 0x0811ABC9 를 원작 ROM 으로 돌리면 +12). 화면 3칸은 반 칸 수 `0x08021F14`: 0→0, 1~47→1, 48~95→2, 96~143→3, 144~191→4, 192~239→5, 240~→6 | 관찰 · ROM 실행 · 해독 |
| +0x5F | 쿨다운(0 이 아니면 그날 관심사 처리 없음, 매일 −1) | 해독 |
| +0x60 | **맞은 화살**(붐 계열 등 화살 종류, 0xFF 없음) — 화살 0x08024440 이 종류 2~5 를 넣고 +0x46(날짜)을 0 으로. 상세 화면 "화살" 줄이 이 값(2·6·8 을 넣어 실기 확인). 힘내라·진정해(+0x69)는 이 줄에 보이지 않는다 | 해독 · 실기 |
| +0x65~0x66 | **신님에게 감사** 개수 (+0x65 아래 바이트, +0x66 위 바이트) | 실기 상세 화면에 칸마다 다른 값을 넣어 확인(11·12 → 3083개) |
| +0x69 | 화살 표시: bit0 효과 중 · bit1 힘내라 · bit2 진정해 | `0x080244A0` 해독 |
| +0x80/+0x82 | 관심사 (표, 번호) | 공략 데이터 save_refs |

### 화살 (ROM `0x080244A0`)
- 힘내라: `표시 |= 3`, 진정해 비트 해제. 진정해: `표시 |= 5`, 힘내라 비트 해제. 쏘는 순간 다른 값은 바뀌지 않는다.
- 효과 중(bit0)에는 힘내라·진정해를 다시 쏠 수 없다(원작 문구 "화살의 효과가 계속되고 있습니다…").
- 표시는 기간이 아니라 **관심사가 끝날 때(MAX/MIN 사건)** 0 으로 풀린다(`0x0802886A`).
- 공략 데이터의 "몰입도 +95 / 0" 설명은 측정과 맞지 않았다(쏜 직후 +0x5B 변화 없음).

### 화살·아이템 (원작 함수, C# OrigSession.Use)
보유 칸: 화살 `0x0202C640`+칸, 아이템 `0x0202C650`+칸 (각 16칸). 실기에서 칸마다 개수를 1·2·3… 으로 넣고 메뉴를 넘겨 확인했다.

| 칸 | 화살 | 아이템 |
|---|---|---|
| 0 | 힘내라 | 하트 열매 |
| 1 | 진정해 | 독 하트 열매 |
| 2 | 태평함 붐 | 액막이 횃불 |
| 3 | 노력 붐 | 행복 상자 |
| 4 | 애정 붐 | 지력의 고리 |
| 5 | 독신 붐 | 체력의 고리 |
| 6 | 마이웨이 | 매력의 고리 |
| 7 | 대망 | 운의 고리 |
| 8 | 선대의 꿈 | 사랑의 고리 |
| 9 | 만남의 예감 | 후계자의 왕관 |
| 10 | 통신 결혼 | 시간의 책갈피 |
| 11 | (미설정) | 선대 마음의 결정 |

- 화살: 쏠 수 있는지 `0x0801CECC(메뉴, 종류)` → 1 이면 맞을 때 `0x08024440(메뉴, 종류, 인물 객체, 메뉴+0x18C)` → 보유 −1(`0x0801CDC2`).
  못 쏘면 `0x0801CECC` 가 메뉴+0x200 에 거절 문구(표 `0x0858683C~`)를 두고 0 을 돌려준다. 힘내라·진정해는 표시 `+0x69 & 6` 이면 거절,
  힘내라는 게이지 0, 진정해는 게이지 255 면 거절. 다른 화살은 나이·직업·연인(+0x74)·배우자(족보+0x14) 등을 본다(문구 자리로 이유를 나눈다).
- 아이템: `0x08024B80(칸, 인물 레코드, 스킬, 메뉴)` 가 0 이면 성공 → 보유 −1(`0x0801D9AE`). 효과:
  하트 열매 +0x5B +95(상한 255), 독 하트 열매 +0x5B = 0, 행복 상자 무드 +64(상한 255), 고리 능력치 +1000(상한 5000, **실기 확인: 지력 2173→3173**,
  참고 자료의 +800 과 다름), 사랑의 고리 연인 있을 때 +0x5D +128, 횃불은 악마(`0x0802A640`)가 있을 때만, 왕관은 세대주의 자녀에게 —
  후계자 `0x0202C67E` = 그 사람, `0x0202C678 |= 4`. 실패 값 1~3.
- 앱이 채우는 메뉴 객체 자리는 "선택 인물 번호 +0x154 = 0, 인물 객체 표 +4" 뿐이다(작업 자리 0x0F038000). 거절 문구 꾸미기 `0x08025240` 은
  화면 함수라 받은 문구 포인터를 그대로 돌려준다("ret1").
- 검증: 시험에서 쓴 화살·아이템 호출 25개를 원작 ROM(unicorn)으로 다시 돌려 메모리가 모두 같음(`replay_check.py`). 실기 지력의 고리 결과와 같음.
- 선대 마음의 결정(칸 11): 고르면 선대의 마음 목록 `0x0202C328`(4바이트씩 최대 99개 — u16 인물 번호, u8 스킬, 끝 0xFFFF)이 "1대 ○○의 마음"으로 뜬다.
  k 번째를 고르면 메뉴+0x18E = 인물, +0x190 = 스킬, +0x192 = 0xFFFF 로 `0x08024B80(100+k, …)` → 스킬 칸(+0x62~0x64)에 넣고(이미 있으면 1,
  칸이 차면 원작이 하나 골라 바꿈) `0x0800F9AC(1, k)` 가 목록에서 뺀다. 목록의 "N대" = 세대 `0x08025DFC(인물)` — 족보의 부모(+0x10/+0x12)를
  거슬러 센다(0 이면 "?"). 실기: 번호 0·1 → 1대, 자녀 2 → 2대, 그 아버지 칸을 지우면 1대 — 변환 트리 결과와 같음. 결정 개수 −1 도 원작 코드 안. 실기와 같음(스킬 5 이어받음, 목록 당김, 결정 1 → 0).
- 시간의 책갈피(칸 10): 아이템 함수가 0x080108BC 로 가족 저장 내용을 세이브 영역 안 책갈피 자리(0x0202C010+0xD2CC~)에 복사한다.
  되돌리기 0x08010AB4(0x0202C678 & 0x80 일 때) — OrigSession.RestoreBookmark. 시험: 쓰고 능력치를 바꾼 뒤 되돌리면 쓴 때 값.
- **가문이 끊김**: 가장(0x0202C67C)이 가장인 채로 죽으면 죽음 처리 0x08114658 이 가문의 기록(0x0801045C: 햇수·재산 등급 0x08118D28)을 남기고
  효과 결과 첫 단어 = 2 → 사건 장면 끝(0x0804DB9C, 장면 +0x288) 이 0x0809AF60(5,2) → 가문이 끊긴 장면 0x0809EAAC("N년 가족" 정리, 책갈피가 있으면 0x08010AB4).
  가장 자리는 후계자가 결혼할 때 넘어간다(장기 진행: 2051 가장 2→4, 2074 4→8 — 결혼식 결과 0x08941400 이 장면 끝 1). 후계자 0x0202C67E 가 죽으면
  다른 자녀(슬롯 0x14~0x16)로, 없으면 0xFFFF. 장면 끝 종류: 1 메인 장면(종류 3), 2 가문 끊김, 3 장면 종류 4, 4 끝 종류 7.
  앱: 결과 2 가 나오거나 가장이 살아 있는 가족에 없으면 진행을 멈추고 되돌리기를 묻는다. 시험: 가장을 원작 죽음 처리로 죽이면 결과 2·끊김, 책갈피로 되돌리면 이어짐.
- 감사의 마음(0x0202C670)·신님 랭크(0x0202C66E): 신님의 정보 화면에서 확인(값을 넣으면 그대로 보임).
- 아직 옮기지 않음: 통신 결혼(통신).
- 얻는 경로: `0x081C4xxx` 영역의 함수들(사건 효과 쪽)이 `0x081148D8(종류, 개수)` 로 보유 수를 정한다 — 종류 0~10 화살 칸, 11~22 아이템 칸(−11),
  0xFE → `0x0202C66E`(u16), 0xFF → `0x0202C670`(u32). 더하기·빼기 판 `0x08115124`·`0x08115230`(상한 99)도 있다(보상 목록 처리 `0x080AF5AC`).
  사건 효과는 원작 코드로 돌므로 앱에서도 원작대로 들어온다. 실기 5일 진행 덤프에서 화살이 5·5 → 7·10 으로 늘어 있었다.

### 사건 결과 스크립트 · 신님에게 감사 · 신님 랭크 (C# OrigResultScript.cs)
- 사건 대사 끝의 글 토큰 `1A 12 00` 이 결과 기록 +0x10 의 **결과 스크립트**로 넘어간다. 글 상자 엔진(0x080A7xxx)은 글을 읽다가
  `1A 12 xx` 를 만나면 해석기 0x080ABA58 의 명령 xx 를 실행한다(분기 표 0x080ABAF4, 명령 0~0x14).
  글 상자 객체 T(실기 중단점 덤프): +0 인물 번호, +4 대상 칸, +0x10 프레임 수, +0x12 반복 횟수, +0x2C 결과 기록, +0x30 묶음 비트,
  프레임 k = T+0x74+0xA0·k (+0 글, +4 위치, +0xC 반복 시작), 명령이 만든 글은 프레임 안 버퍼(+0x20)에 써서 새 프레임으로 쌓는다.
- 명령: 0 결과 스크립트 시작, 2 대상마다 반복 시작(손 이식 — k 번째 비트 찾기 반복), 3 반복 끝, 4 쪽 넘김, 5-0x26 **랭크 확인**,
  6 변화 표시, 8 **감사**(인자 0xFF 뒤 숫자), 그 밖은 표시·연출.
- 감사(명령 8 → 0x080AE144): 인물이 **마이웨이의 화살**(+0x60 = 6)이면 2배, 아니면 **화살 효과 중**(+0x69 bit0)일 때만 —
  감사의 마음 0x0202C670(최대 999999)과 그 인물 +0x65~0x66 에 더한다. 화살 없이 이룬 일에는 감사가 없다.
  양은 결과마다 정해져 있다(결과 스크립트의 `1A 12 08 FF 00 nn`): 결과 기록 5,312개 중 1,887개 — 5(692개)·2(461)·7(403)·10(158)·20(84)·4·3·15·50(4, 청혼 등)·1·6.
  관심사가 이루어진 결과(MAX, 힘내라)뿐 아니라 식어서 끝난 결과(MIN, 진정해 — 예 "안심했어…" 2)도 감사를 준다.
- 랭크 확인(0x080AC8B4): 감사의 마음 ≥ 다음 랭크 기준(0x0811A6E4(랭크+1)) 이면 랭크 +1(최대 50), 보상 목록(0x0811A6B4(랭크) → 0x080AF5AC)으로 화살·아이템.
- **순서**(실기 감시, 같은 시작 상태): 대사 끝(명령 0) 7811 → 감사 +5 8051 → 랭크 0→1·화살 4·5→10·10 8241 → 효과 쪽 0x0802886A 가 화살 표시 해제 9560 프레임.
  즉 결과 스크립트는 사건 효과 함수보다 먼저 돈다. 앱(OrigEvents.RunScene)도 시작 함수 → 결과 스크립트 → 효과 함수 순서.
- 검증: main.ram 에서 C# 원작 진행 첫날 감사의 마음 0→5, 랭크 1, 화살 10·10, 인물0 감사 5 — 실기와 같음.
  2년 진행 시험에서 감사의 마음 177, 랭크 10 까지 오른다(이전에는 0 이었다 — 결과 스크립트를 돌리지 않아서).
- **결과 문구**: 글 상자가 낼 글(글자·줄/장 바꿈·이름)을 OrigResultScript 가 모아 DayEvent.Shown 에 담고, 번역 패치 글자표(아래)로 풀어
  대사 뒤에 원작 문구 그대로 붙인다(대상 머리글, 하트·무드 변화, 감사 수, 감사의 마음 합계, 랭크 상승, 보상 안내).
  - 글 엔진 토큰 분기(0x080A7138): 1 줄바꿈 0x080A73E0, 2 0x080A74A0, 3 색 0x080A7520, 5 숫자 0x080AB774, 6 값 자리 0x080A796C, 8 0x080A77D4,
    9 0x080A7438, 0A 0x080A75F0, 0B 0x080AB5FC, 0C 0x080AB6B8, 0E 0x080AAC44, 0F 0x080AAD50, 10 0x080AAA90, 11 0x080A774C, 12 해석기, FF 프레임 닫기 0x080A7370.
    숫자(1A 05)·값 자리(1A 06 aa bb)는 원작 함수(변환 트리)를 불러 글을 새 프레임으로 쌓는다 — 예 1A 06 26 10 = 감사의 마음 합계(÷10000·나머지로 자리 나눔).
    1A 06 aa: 0~0x1B 슬롯표 인물(0x080A7AD4), 0x1C 배우자 쪽(0x080A81F0), 0x26 bb=1 플레이어 이름(0x0202C660), 0x27 가문 이름(0x0202C6A0) 등.
  - 0 바이트: 프레임 +8 이 0 이 아니면 프레임을 닫고(0x080A6852~), 아니면 건너뛴다.
  - 명령 2 머리글(0x080AC414~, 손 이식): 글 표 0x085C081C +0x314 (머리글 앞부분) + (인자 0x22 면 +0x31C 가족 전체 문구, 아니면 색·대상 이름(족보 +0x20)·+0x318 조사 문구).
  - 이름: 원작은 이름을 메모리 이름 칸(족보 +0x20 14바이트, 가문 0x0202C6A0, 플레이어 0x0202C660)에서 가져온다. 앱은 한국식 이름을 따로 가지므로
    결과 스크립트를 도는 동안 그 칸에 앱 전용 표지 `1A 86 b1 b2 00`(번호를 7비트씩 0x80 더해 0 바이트 없게)을 넣었다가 되돌리고, 표지를 앱 이름으로 바꾼다.
    플레이어 이름은 앱에 입력 화면이 없어 "신님"(앱 기본값).
  - 번역 패치가 옮기지 않은 일본어 글(랭크 3 이상 보상 설명 일부 — 가나가 남아 있고 한자 자리는 패치 글꼴의 한글이라 실기에서도 뜻이 안 통한다)은 빼고,
    "[앱 요약] 받은 것: …" 한 장으로 대신한다. 글자표가 없으면 감사·랭크·받은 것을 앱 문장으로 요약한다(역시 "[앱 요약]" 표시).
- 글 토큰 길이: 01·02·09·0D 2, 03·0A 3, 05·06·08·0B·0F 4, 10 5, 0E 하위 명령 00→4·01→7·02→5 (참고 대사·ROM 글에서 확인).

### 관심사 하루 처리 (ROM `0x08027E78`, 인물마다 매일)
```
if 게이지 == 255: (요일 조건을 만족하면) MAX 사건   — 아니면 그날은 아무 일 없음
elif 게이지 == 0: (요일 조건을 만족하면) MIN 사건
else:
    if 표시 & 2:  게이지 = min(255, 게이지 + 32)          # 힘내라
    elif 표시 & 4: 게이지 = max(0, 게이지 − 64)            # 진정해
    elif 날짜 < T: 게이지 = min(255, 게이지 + (난수&15) + 4)
    else:         게이지 = max(0, 게이지 − ((난수&31) + 48))
    날짜 += 1
T (0x080288A8) = 성격 코드나 관심사 유형이 0 이면 11, 같으면 12, 다르면 10
```
- 사건이 나면 게이지 136 · 날짜 1 · 화살 표시 0 으로 새로 시작(`0x08028830`, `0x0802886A`).
- 요일 조건(`0x080281E8~`): 사건 항목 +1 이 3 이면 아무 날, 2 면 직업 요일표의 비트, 1 이면 그 반대. 직업 요일표 = `0x0889D3B8[직업]` +4 (7비트, bit0 일요일 — 1950-01-01 기준 계산 `0x08095C18`).
- 측정과 일치: 화살 없이 오름 10~12일 → 하루 −48~−79 로 떨어져 0 → MIN 사건(관심사 하나 ≈ 15일). 힘내라 → 하루 +32 로 255 → MAX 사건. 진정해 → 하루 −64 로 0 → MIN 사건.

### 관심사 표 (ROM `0x085BD4A0[표][번호]`)
- +0x0F 관심사 유형, +0x1C MAX 사건 항목, +0x20 MIN 사건 항목.
- 사건 항목(0x28 바이트): +1 요일 조건, +0x18/+0x1C 함수, +0x24 **변형 목록**(포인터 → [판정 함수, 대본]).
- 변형의 판정 함수 주소가 공략 데이터의 `variant_predicates` 와 같다 → `tools/import_original_pack.py --rom` 이 MAX/MIN 결과 목록을 정확히 만든다. MIN 사건은 여러 관심사가 함께 쓰는 공용 사건이고 그 변형들은 `events-ko.json` 쪽에 있다.

## 원작 코드 자동 변환 (tools/romlift)
원작 판정 함수는 최적화하지 않은 Thumb 코드라 기계적으로 옮길 수 있다.
- `lift.py`: 함수 하나를 기호 실행해 **결정 트리**(분기·호출·메모리 읽기/쓰기)로 바꾼다. 보조 함수는 따로 변환한 트리를 호출한다.
  스택 주소를 넘기는 호출은 펼쳐 넣는다. 반복 범위가 데이터에 따라 달라 트리로 못 바꾸는 것만 C# 으로 손 이식한다.
- 손 이식(검증 완료): 난수 `0x08000614`, 나머지 `0x0824F640`, 관계 판정 `0x08115778` 과 관계 슬롯표 작성 `0x08110B90`
  (`Core/Orig/OrigFamily.cs`).
- `export_orig.py`: 관심사 1,109개 전부의 판정 트리(+보조 함수 트리 48개)·후보 목록·선택 표·직업/특별 후보표·트리가 읽는 ROM 표 조각을
  로컬 JSON(약 670KB)으로 뽑는다. **로컬 전용**.
- 검증: `romcall.py`(unicorn, 검증 전용)로 원작 함수를 실제 RAM 덤프(`capture` 의 `ramdump`) 위에서 돌려 비교.
  - 파이썬 변환 트리: 덤프 7개 × 가족 4명 × 관심사 판정 897종 = 25,116건 원작과 같음.
  - 관계 슬롯표 287건, 관계 판정 15,512건 같음.
  - **C# 실행기**(`Core/Orig/OrigVm.cs`): 판정 13,308건, 관심사 선택 96건(메모리 변화 바이트 단위) 원작과 같음
    (`tests/Core.Tests`, 환경변수 `SK_ORIG_DIR` 에 로컬 자료가 있을 때).

### 원작 메모리 배치 (Core/Orig/OrigMem.cs)
- 원작 세이브 영역 = EWRAM `0x0202C010~0x0203C440` (플래시 세이브 앞부분과 같은 배치). 가족 레코드 `0x0202C6C4+976n`(8명),
  족보 `0x0202EB9C+60×번호`(+0x10 아버지 · +0x12 어머니 · +0x14 배우자 · +0x16 자녀 4 · +0x31 성별), 관계 슬롯표 `0x0203C3E0`.
- 가족 레코드 앞 60바이트는 족보 레코드와 같은 배치(+0x2E 생일 {u16 년, u8 월, u8 일}, +0x31 성별, +0x3C 번호).
- EWRAM 은 256KB 마다 반복된다. 원작은 없는 사람(0xFFFF)의 족보를 읽을 때 이 반복 주소를 읽는다 → 그대로 재현.

### 인물 속성 (ROM 0x08116734, 판정 함수가 쓰는 49가지)
0~3 능력치(+0x50~+0x56)에 관심사 보정: 성격 코드 = 관심사 유형이면 ×1.25(최대 5000), 내향↔외향 반대면 ×0.75, 그다음 스킬 3칸(+0x62~64,
스킬표 `0x088A309C`) 보정 합. 4 게이지(+0x5A) · 5 하트(+0x5B) · 6 +0x5D · 7 +0x5E · 13 +0x40 · 14/15 관심사 표/번호 · 17 관심사 유형 ·
18 직업 분류 · 19 직업(+0x58) · 20 직급(+0x59) · 24 성별(+0x31) · 25/26 +0x32 상·하위 4비트 · 27 나이 · 28 나이 단계 · 29~31 스킬 ·
34 +0x61 · 35 상태(+0x60) · 36 화살 효과 중 · 37 수입 계산 · 41~44 +0x5C 비트들 · 45~48 능력치 원값.
배우자 후보(교제 상대) 값은 +0x6A~+0x74 (`0x08117168`), 가족 전체 값은 `0x08111D54`(무드·자산·시대 등).

### 다음 관심사 선택 (ROM 0x08028524, C# Core/Orig/OrigSelect.cs)
```
mode = 5
if +0x61 & 8:  표 3(유형 = +0x61&3 인 것)에서 뽑기, +0x61 = 0
elif 상태(+0x60) == 2: 2/3 확률로 mode 0
elif 상태 == 4:        2/3 확률로 mode 2
else: +0x3E 특별 후보표가 있으면 항목마다 (난수&255) < 확률 이고 성별·판정 통과하면 그것
      없고 상태 == 3 이면 2/3 확률로 mode 1(직업)
mode 5 이면: b15 = 0x08584D24[난수%3], mode = 0x08584CA4[나이 단계][난수&15]
mode 0/2: 표 0/2 의 후보 목록 0x085BD4B4[표][나이 단계][시대] 에서 무작위 — 성별 조건(+0x10: 2 누구나)과 판정 함수를 통과할 때까지
          (지금 관심사와 같으면 한 번만 다시 뽑음)
mode 1:   직업 후보 (0x081191A4: 직업 → b15 로 다른 직업표 → 공통 목록 + 직급 목록에서 무작위)
선택 결과는 대기표(0x0203BD20/0x0203BD40)에 넣고, 게이지 = 관심사 +0x12(136·140·160·216 등), 날짜 = 1, 화살 표시 해제
대기표는 0x080289C4 가 가족 레코드 +0x80 에 옮긴다.
나이 단계(0x08111888): ≤3 · ≤6 · ≤12 · ≤15 · ≤22 · ≤34 · ≤60 · 그 위.  시대(0x08111A58): 가족 +0x683 의 날짜 목록 중 지난 수.
```
- 새 관심사 시작 게이지는 136 고정이 아니라 관심사마다 다르다(136 770개, 140 71개, 216 41개, 160 13개 …).
- 원작이 초기화하지 않은 지역 변수(b15)를 쓰는 경로가 있다(상태 3 → 직업). 그 값은 재현할 수 없어 0 으로 둔다.

### MAX/MIN 사건의 진행 (해독 중)
- 하루 처리(0x08027E78)는 결과 코드를 돌려준다. 받은 인물 행동 루틴(0x08011D30)이 0x08014370 으로 사건 항목을 정한다:
  | 코드 | 사건 |
  |---|---|
  | 1 / 2 | 지금 관심사 +0x1C(MAX) / +0x20(MIN) |
  | 3 | 그 사람의 일정 목록(+0x76~, 0x08026D74)에서 꺼낸 사건 |
  | 4 | 가족 공용 일정(0x08027090) |
  | 6 / 7 / 8 | 특별 사건 표 4·5·3 의 +0x4A / +0x4C / +0x4E 번 (0x08119C5C) |
  0 이면 사건 없음. 하루 처리 자체는 변환 트리로 원작과 64건 모두 같음.
- 관심사 밖의 사건 기록도 같은 0x28 바이트 배치다(ROM 에서 7,350개). 모두 변환 대상에 넣었다.
- **변형 고르기 (0x08119CA0)**: 사건 항목 +3 = 변형 수 n, +0x24 = 변형 목록. 앞에서부터 판정 함수가 참인 첫 변형을 쓰고,
  하나도 참이 아니면 목록의 n 번째(끝 다음) 항목을 쓴다. 변형 = [판정 함수, 결과 기록(0x30 바이트)].
- 결과 기록 +0x18 함수는 사건 시작 때(0x0804C84A, 대사에 넣을 이름 등 문장 준비), +0x1C 함수는 사건이 끝날 때
  (0x0804D9B2) 호출된다 — **+0x1C 가 효과 함수**: 능력치 변화(0x08115CD0: 슬롯·속성·변화량, 몰입도·상태 보정 포함),
  다음 관심사(0x081132D4: 정해진 관심사 또는 무작위 선택 0x08028524), 사건 마무리(0x081125A4) 등을 차례로 부른다.
  실행 중단점으로 원작 실행에서 확인.
- 관심사가 시작될 때 원작은 결과를 미리 하나 정해 두는 예정표도 만든다(0x0802ADB0: 시작 게이지 216 이상이면 100%,
  성격=유형이면 85%, 한쪽이 0 이면 66%, 다르면 35% 확률로 MAX, 날짜는 오늘+10~12일(MAX)/13~15일(MIN)). 쓰이는 곳은 미확인.

### 새 가족 만들기 — 추천 가족 (C# Core/Orig/OrigNewGame.cs)
- 공식 소개 페이지("まずは家族をつくろう")에 따르면 시작 가족은 두 가지다: 신이 추천하는 가족, 또는 플레이어가 직접 정한 가족.
  공식 페이지에는 전원이 꺼져 있는 동안에도 게임 시간이 흐른다고도 적혀 있다. 이 페이지에서 확인한 것은 이 사실뿐이다(규칙 수치는 없음).
- 원작 순서 (실행 중단점·쓰기 감시로 확인):
  | 단계 | 원작 | 하는 일 | 앱 |
  |---|---|---|---|
  | 장면 시작 | 0x0804134C | 설정 블록(0x02001AF0) 머리말 0x44·구성원 8×0x9F0 바이트를 0xFF 로(DMA 채우기 0x08049CC8/0x08049C20), 구성원 +0xE·+0x4C = 0, 0x0202C6A0 = 0. 시작 날짜 = 카트리지 시계 날짜(0x0202C688), 없으면 2005-01-01 | 손으로 옮김 (`Init`) |
  | 추천 가족 틀 | 0x0804BC2C | 성(姓) = 0x088A3F84[난수&0xFF] (256개), 틀 = 0x08587DBC[난수&7] (20바이트): +0 구성 비트 → +0x28, +1 아이 성별 비트 → +0x1C..1F, +2 → +8, +3..+0xA 나이 기준·+0xB..+0x12 나이 폭 → 구성원 +0x4E/+0x4F | 변환 트리 |
  | 확인 화면 시작 | 0x0802C9A0 | 구성 비트 수 → +0x29 인원, 비트 차례로 구성원 관계 +0x4D: 비트 0→0, 1→1, 2→2, 3→4, 4~7→(+0x1C+비트-4)==0 이면 6 아니면 7 | 손으로 옮김 (`Confirm`) |
  | 구성원 마무리 | 0x0802D7A0 (+0xD340 = 1) | 역할표·비트 순서 정리, 구성원마다 채우기 0x0804B1F0(능력 순위 섞기, 나이 = +0x50 + 난수 % +0x4F, 관계별 성별, 아이 생일 무작위 등), 아이(6·7)는 0x08049AF0(부모 설정에서 물려받기) | 변환 트리 |
  | 확인 결정 | (화면) | +0xD34A = 0. 0 이 아니면 다음 단계가 가족을 만들지 않고 끝난다 | 0 을 넣음 |
  | 가족 레코드 만들기 | 0x080417E0 | 구성원마다 0x0804A190 으로 인물 레코드, 0x08028BAC 생일순 삽입, 관심사·직업 등 시작 상태(0x081132D4 등), 0x080DD4B8·0x08011168 | 변환 트리 |
- 원작이 건너뛰어도 되는 함수(네이티브 noop): 장면 객체 128개 정리 0x08001014(건너뛰어도 원작 결과 EWRAM 전체 동일), 다음 장면으로 바꾸기
  0x0809AF60(건너뛰면 저장 범위 안에서는 0x0203BE04 = 장면 작업 핸들만 다름), 마무리 장면 끝의 화면 정리 함수들.
- 원작 코드 일부는 DMA(0x040000B0~DF)로 메모리를 채우거나 복사한다. C# 메모리 모델과 검증용 unicorn 실행기 모두 즉시 시작 DMA 를 흉내 낸다.
  변환기는 지역 변수 주소가 메모리(예: DMA 원본 레지스터)로 나가면 그 전에 스택 값을 프레임 메모리에 쓴다.
- 검증: 구성원 마무리는 원작 덤프에서 설정 블록·저장 영역 0바이트 차이. 가족 레코드 만들기는 실제 기계 덤프(mGBA, 0x080423F2 지점)와 비교해
  11바이트만 다르다 — 가족 머리말(0x0202C6A0, 36바이트)의 성 문자열 끝(NUL) 다음 칸과 구조체 패딩으로, 원작이 스택에 만든 구조체를 통째로
  복사(0x0800F770)해서 들어가는 스택 찌꺼기다(실제 기계와 unicorn 도 서로 다른 값). 재현하지 않는다.
- 팩의 ROM 조각: 새 가족 코드는 난수에 따라 다른 표 항목을 읽어서, 원작 코드를 seed 2048개로 돌려 읽은 ROM 범위를 1KB 단위로 모았다
  (`tools/romlift/newgame_spans.py`, 1,500번째쯤부터 늘지 않음, 33구간 283KB). 그래도 못 본 항목을 읽으면 앱은 "팩에 없는 ROM 표"로 멈춘다.
- 빈 카트리지에서 시작하기 (`BlankCartridge`, `TitleNewGame`): 전원을 켜면 원작은 플래시 세이브를 0x0202C010 부터 읽는다(세이브가 없으면 0xFF,
  원작 실행에서 0xFF 범위는 0x0203BA38 앞까지, 그 뒤는 0). 이어 저장 영역 초기화 0x0800D778(0). 제목 화면 시작이 0x0802B194(0x0203BD30~32 = 0xFF),
  새로 시작을 고르면 0x0800D778(1 또는 2; 0x0202C030 의 0x40 비트). 이렇게 만든 저장 영역은 원작의 새 가족 장면 직전 상태와
  날짜·성·화면 작업 변수(0x0203BD68)·장면 핸들(0x0203BE04)을 빼고 모두 같다.
- 원작 힙: 할당 0x08006A58, 해제 0x0800695C(머리 0x0202BFB0). 아이 외모 만들기(0x08107B60 → 0x080BE1CC)가 0x302C 바이트 작업 버퍼를 잡는다.
  앱은 원작 힙 상태를 두지 않고 따로 잡은 작업 영역에서 할당하고 해제는 하지 않는다(맨 바깥 호출마다 처음부터).
- 그렇게 만든 가족을 원작 하루 처리로 60일 돌리면 예외 없이 사건 14번이 난다(이 진행 자체는 원작 실행과 아직 비교하지 않았다).
- 이름 입력 화면(0x0202C660 14바이트 등)은 옮기지 않았다(앱이 한국식 표시 이름을 쓴다). 플레이어가 직접 정하는 가족은 아래 "내가 아는 가족".

### 새 가족 만들기 — 내가 아는 가족 (C# OrigNewGame.Custom, OrigSession.NewCustom)
실기(mGBA)에서 "어… 잠깐만요…"로 가족을 직접 만들며 쓰기 감시·중단점으로 잰 순서:
1. 가족 구성 화면: 설정 블록 +0x28 구성 비트(0 조부 · 1 조모 · 2 부 · 3 모 · 4~7 자녀 칸), 자녀 성별 +0x1C+칸(0 아들 · 1 딸).
2. 구성 확인(0x0802CA1C/0x0802CAF8 — Confirm): +0x29 인원, 구성원 +0x4D 관계 코드.
3. 마무리 0x0802D7A0 (+0xD340 = 0 경로): 머리 +0x08, 역할 번호 +0x10~, 구성원 성별 +0x20, +0x40, +0x48 기본값.
4. 구성원마다 입력 화면 → 임시 구조체(0x0200F254: [0] 설정 블록, +0x14 완료 비트 포인터, +0x1C/+0x1E/+0x20 생일, +0x24/+0x26 나이,
   +0x28 성별, +0x29 혈액형(A·B·O·AB·? 순), +0x2A 성격(내향·보통·외향 순), +0x2B 직업 번호, +0xC5C 이름) → 확인 0x08037344(원작 함수 그대로 부름:
   생일·혈액형·성격·직업(+0x2E)·능력 순위 역표(+0x51~)·나이(0x08095D3C)·나이 단계(0x08097398), 6세 이하는 부모 외형에서 0x08049AF0).
   능력 순위 화면은 +0x55~+0x58(순위별 능력 번호), 직업 화면은 후보 목록 0x081114CC(+0x5C 수 · +0x60~ 4바이트씩)와 고른 번호 +0x59.
   직업 후보 종류는 관계 코드 0·1·2·4 면 0x14, 자녀면 0x24. 체격 +0x48, 캐릭터 +0x30~+0x3F(목록은 화면이 그때그때 무작위로 만든다, 0x08048B4C), 완료 +0x4C.
5. 가족 레코드 만들기 0x080417E0 (추천 가족과 같은 함수).
검증: 실기 입력(아버지·어머니 1986-01-01, 아들 2004-01-01, 기본 선택)과 같은 값을 넣으면 만들기 직전 설정 블록(머리말 + 구성원 3명)이 실기와 0바이트 다름.
그 위에서 C# 만들기 = 원작 ROM 실행(머리말의 스택 찌꺼기 13바이트 제외 — 추천 가족 때와 같은 현상).
앱 입력(FamilySetup) → NewCustom: 생일·성별·직업·외형 자리 등 정해지는 값은 실기 만들기와 같고, 능력치는 원작 만들기 함수가 난수로 정한다.
앱에서 정하지 않는 값: 외형 바이트는 실기 캐릭터 화면이 만든 한 예(성별별) — 판정 속성 49종이 읽지 않는 값, 화면 외형은 앱 Look.
직업 이름(OrigJobs): 원작 직업 화면에서 읽었다(0~13, 15~27, 29, 30). 그 밖의 번호는 "직업 #번호".

### 하루의 흐름 (C# Core/Orig/OrigGame.cs `TickDay`)
실행 중단점·쓰기 감시로 측정한 원작 순서:
1. **날 바뀜** (메인 장면 0x0801862C 안, 0x080193EC~): 날짜 +1(0x08095DAC) → 0x0202C684 에 저장. 날짜·경과일 표시(0x08021FE0, 0x08022208)는 화면.
   시작 날짜부터 1000년째(0x0802B2A4)면 특별 사건 표 2 를 사건 큐에 넣는다.
2. **06:00**(하루 시각 0x708, 하루 7200) 이 지나면 인물 작업(0x08011D30, 작업 버퍼 0x282C 바이트)마다 한 번:
   - 생일(작업 +0x281E/+0x281F 에 둔 레코드 생일, 2/29 생은 평년 3/1)이면 그 인물 슬롯표 → 특별 사건 표 2 의 2 번 변형 → 사건 큐 {결과, 종류 0, 인물}
   - 관심사 하루 처리 0x08027E78 → 결과 코드로 그날 사건(작업 +0xDBC)과 하루 일정(+0xDB8 = 사건 +0x20) 정하기 (0x08014370):
     | 코드 | 그날 사건 |
     |---|---|
     | 1 / 2 | 지금 관심사 항목 +0x1C / +0x20 |
     | 3 | 0x08026D74(레코드, 결과): 결과 +8 사건, +4 → 레코드 +0x5F |
     | 4 | 0x08027090(0, 결과, ·): 결과 +8 사건, +0 대상 작업 번호(-1 이면 0x0202C67C 인물만), +4 → 레코드 +0x5F |
     | 5 | 없음 |
     | 6 / 7 / 8 | 특별 사건 표 4·5·3 의 +0x4A / +0x4C / +0x4E 번 |
   - 그날 사건이 없으면 직업 요일(0x0811A19C·0x08023F68)에 따라 관심사 활동(0x08119E78) 또는 직업 기본 활동(0x08119E34, 0x0202C692) 일정.
   - 하루 일정 = 명령 목록 해석기 0x08014610 (명령 표 0x08581558, 15가지). 걷기·방 이동·표정 같은 화면 명령이고, 규칙 상태를 바꾸는 것은
     명령 8(0x080153B0) 하나: 사건 큐에 {0, 종류 6, 인물} 을 넣는다. 측정한 25일 동안 그날 사건이 정해진 날은 모두 곧바로(약 80프레임 뒤) 큐에 들어갔다.
3. **사건 큐** (0x0203BBC0, 저장 영역): +8 쓰는 번호, +0xA 읽는 번호, 0x0203BBD0 부터 24칸 {결과 u32, 종류 u16, 인물 번호 u16}.
   메인 장면이 하나씩 꺼낸다(0x08018642~). 종류 6 은 이때 0x08110B90(인물, 그날 사건) 슬롯표 → 변형 고르기. 결과 +0 이 5 초과·0xB 아니고
   그 인물이 그날 새 관심사를 알렸으면(작업 +0xDD0 의 0x2000) 띄우지 않는다.
4. **사건 장면** (큐 작업 0x0801E724 → 장면 시작 0x0804C66C): 먼저 0x0800E57C(인물 레코드 앞 0x38바이트 → 가계 표 0x0202EB9C + 60×번호)와
   0x08110B90(사건 인물, 0) 으로 사건 인물 중심 슬롯표를 다시 만든다(실기 중단점으로 확인 — 큐에 넣은 뒤 다른 인물 처리가 슬롯표를 바꿔도 여기서 바로잡힘).
   그다음 시작 함수 결과 +0x18(돌려준 값 → 장면 +0x286; 5,311개 중 약 170개만 0 이 아닌 값) →
   참가 슬롯 0x08110F5C(그 값) → 효과 함수 +0x1C(결과 버퍼, 그 값) → 끝 처리 0x0804DB50(큐피트 도움말, 아래) →
   메인 장면 복귀 0x080111B8(-3, 인물, 1, ·, 그 값, ·, 결과): 인물 추억 목록(레코드 +0x84, 8바이트 × 최대 100, 개수 +0x68)에 기록(0x0800EC58),
   결과 +0 종류에 따라 후속 일정(0x08026D74 / 0x08027090), 날 넘김 조건 등.
   - **큐 머리와 날 끝내기**: 메인 장면을 떠날 때(0x080211F4·0x080213EC) 큐 머리 +6 에 가족 수(0x08015BC4, 레코드 +0x3C 가 0xFFFF 아닌 수),
     +0xE 에 가족 표지((0x0202C6AF & 0xF) + (0x0202C692 << 8)) 를 적는다. 0x080111B8 은 둘이 지금 값과 같으면 그냥 돌아가고, 다르면
     (사건으로 가족이 바뀜) 날짜 +1 → 0x0202C684, 시각 06:00, 작업 표(0x0203BAE0 + 0x1C×i, +0xE) 를 0xFFFF 로 지우고 메인 장면을 다시 시작한다.
     이때는 메인 장면의 자정 넘김(월초·1000년 사건)과 03:00 을 지나지 않는다. 원작 덤프 40여 개에서 머리 값은 언제나 가족 수·표지와 같았다.
   - 일정 풀(0x02038BEC, 12바이트 칸): {u32 날 번호(0x08027D0C), 사건 주소 아래 3바이트(+4~+6, 0x08000000 을 더함), +7 → 레코드 +0x5F,
     +8 주인(10 이상이면 가족 일정: 대상 작업 = 값-10), +9 다음 칸}. 0x02038F70 = 날 순 목록 머리, 0x02038F71 = 빈 칸 목록,
     0x02038F72~ 11개 = 묶음별 목록 머리. 0x08027090(방식, 결과) 은 묶음 머리들 중 날이 가장 이른 칸을 결과로 낸다(방식 1 이면 지움).
     인물의 일정 사건(예: 출근·통학처럼 효과 함수가 다음 날 일정을 다시 넣는 것)은 매일 이어질 수 있다.
5. 장면 뒤 큐 작업이 대기 중인 다음 관심사(0x0203BD20 인물 / 0x0203BD40 관심사)를 하나씩 레코드 +0x80 에 넣고(0x08028AAC) "새 관심사"를 알린다.

검증 (원작 실행 덤프 대조, `SK_DAYS_DIR`·`SK_PICKS_DIR`·`SK_SCENES_DIR` 로컬 시험):
- 메인 장면 변형 고르기 지점 7건: 슬롯표(사건 인자 경로 포함)+변형이 원작과 모두 같음.
- 사건 장면 효과+복귀 6건 중 5건 저장 영역 동일. 1건은 0x0203BD30(도움말 기록) 1바이트 — 0x0804DB50 미이식.
- 날 바뀜 덤프에서 C# 하루 → 다음 날 바뀜 덤프: 사건이 난 날·인물·종류는 같지만 바이트까지 같은 날은 없다. 원작은 화면 연출에서도 난수를 계속 써서
  06:00 이나 사건 때의 난수 값이 C# 와 달라지기 때문(관심사 게이지 하루 변화량, 다음 관심사 고르기 등). 같은 지점의 난수에서 시작하면 위처럼 같다.
- 하루 시각(0x0202C682)·작업 위치표(0x0203BC90~)·작업별 하루 활동 결과(0x0203BAD4~, 0x1C 바이트 × 인물)는 C# 가 아직 만들지 않는다.
- **장기 진행 재실행 비교** (`tools/romlift/replay_check.py`): 장기 진행 시험이 `SK_REC_DIR`·`SK_REC_FROM`·`SK_REC_DAYS` 로 맨 바깥 원작 함수 호출의
  앞뒤 메모리(EWRAM·IWRAM·결과 버퍼)를 남기면, 같은 호출을 원작 ROM(unicorn, 화면 함수는 바로 돌아오게, 힙 할당은 앱과 같은 규칙)으로 다시 실행해
  바이트 단위로 비교한다. 진행 중 아무 날이나 골라 변환 트리 = 원작 실행인지 확인할 수 있다.
  이 방법으로 찾은 것: (1) 큐 머리를 적지 않아 사건마다 날이 넘어가던 문제(위), (2) 변환기 합류 처리에서 한쪽 가지에서만 쓴 스택 칸을 버리던 문제
  (0x08027090 의 "가장 이른 묶음 번호" 바이트가 쓰레기가 되어 가족 일정이 영영 처리되지 않음 → lift.py merge 수정, 전체 다시 변환 `--relift`).

메인 장면의 시각별 처리 (0x080193EC~0x080198E4, 하루 시각 7200 = 24시간, 한 프레임에 하나만):
| 언제 | 원작 | 하는 일 |
|---|---|---|
| 날 바뀜 | 0x080194A2~ | 경과 년수(0x0802B2A4) 1000 이면 특별 사건 표 2 의 3 번 → 큐 종류 4. 1일이면 표 2 의 0 번 → 종류 1 (대상 = 가장 0x0202C67C) |
| 03:00(900) 이후 하루 한 번 | 0x0801971C~ | 레코드 +0x61 이 0 아닌 첫 인물(0x0802A640)이 4 비트면 +0x61 = 0x0802A7DC(경과 년수: 100·400·700 넘으면 1·2·3)+8, 그 인물로 장면 0x0801FF70 |
| 06:00 | 인물 작업 | 위 "06:00" 블록. 블록 끝에 0x0802A6C4(인물) 이 참이면 레코드 +0x61 = 4 (나이 단계·관심사·+0x4B 에 따라 1/4·1/16 확률) |
| 20:00(6000) 이후 | 0x08019818~ | 1년 중 날(0x08027D0C) 로 가족 일정표(0x02038FC0, 12바이트, 다음 번호 0x02039128) 에서 날이 된 일정(0x08027BE4)을 꺼내 → 그 인물 슬롯표 → 변형 → 큐 종류 3. 없으면 그날 끝 |
| 22:00(6600) 이후 하루 한 번 | 0x08019600~ | 그 달 마지막 날(0x08095CD0)이면 특별 사건 표 2 의 1 번 → 종류 2 (가장) |
- 레코드 +0x61 장치: 공식 소개의 "시대가 진행될수록 강한 아크마가 온다"와 맞는다(경과 년수 단계). 원작에서 +0x61=4 를 일부러 넣어 돌리면
  다음 날 03:00 이후 +0x61 = 8 이 되고 0x0801FF70 장면이 돈다. 레코드가 지워지지는 않았다(사망 장치는 아직 못 찾음).
- 원작 실행에서 월말(종류 2, 2월 28일 밤)·월초(종류 1, 3월 1일) 사건도 인물 사건과 같은 사건 장면 경로(시작 → 효과 → 0x080111B8 복귀)로 처리됨을 확인.

가족 변화 (장기 진행 20년, 추천 가족 1957·1965·1986년생):
- 결혼: 가족 일정(묶음 목록)의 사건 0x08941FC0 — 변형의 시작 함수(0x081FF0B9 등, 참고 자료 제목 "행복이 가득한 결혼식♪"·"꿈꾸던 결혼식")가
  레코드 넣기 0x0811305C 로 배우자 레코드를 만든다. 출생: 사건 0x08942010(시작 함수 0x081FF921 → 0x081141D8, "건강한 아기를 출산").
  사망: 사건 0x08942038 의 효과(예: 0x081FFC91, "가족이 지켜보는 가운데 작별")가 레코드를 지우고 가계 표에 날짜를 적는다.
- 이번 이식에서 20년 동안 아들 결혼(2020년)·손녀(2020년)·손자(2022년) 출생이 일어났다. 결혼·출생 날을 포함한 4개 구간(8일, 호출 253건)을
  원작 ROM 재실행과 바이트 비교해 모두 같았다.
- 80년 진행(29,200일, 사건 14,524번)에서는 손자 독립(2041, 19세)·할아버지 사망(2044, 87세)·손녀 결혼(데릴사위 합류, 2051)·
  증손 출생 3번·할머니 사망(2056)·아들 사망(2073)·증손 결혼과 형제 독립(2074) 등 세대교체가 이어졌다. 2041·2044·2074년 구간
  호출 229건도 원작 ROM 재실행과 모두 같았다. 진행 전체가 원작 실기와 같은 난수 흐름을 따르지는 않으므로(화면 연출이 난수를 씀)
  날짜·횟수는 실기 한 판과 다를 수 있다.

확인한 화면 전용 처리(규칙 상태를 바꾸지 않음 — 옮기지 않음):
- 아크마 장면 0x0801FF70~0x08020248: 실기에서 +0x61=4 를 넣어 장면이 돈 앞뒤 세이브 영역을 비교하니 작업 위치표(0x0203BC90)만 바뀌었다.
  0x0802A898 은 아크마 그림 종류(+0x61 하위 2비트)를 읽기만 한다. 아크마 상태(+0x61) 설정은 TickDay 에 이식돼 있다.
- 전원이 꺼진 동안의 진행: 카트리지 시계를 며칠 앞당겨도 날짜가 건너뛰지 않았다(위 "시간") — 원작은 꺼진 동안 진행하지 않는다.

미이식:
- 사건 장면 끝 큐피트 도움말 0x0804DB50(0x0202C034 비트, 0x0203BD30 기록) — 한 번만 보여 주는 안내로 보임.
- 아크마 장면(0x0801FF70~0x08020248)의 화면 처리, 장면 시작에서 시작 함수를 건너뛰는 조건(장면 +0x54 가 0·4 가 아닐 때),
  하루 일정 명령 8 의 정확한 시각(한 날 여러 사건의 순서), 인물 작업 +0x5F 일정.

### 번역 패치 글자표 (tools/romlift/export_charset.py → orig_text.json "charset", C# OrigText.Decode)
- 번역 패치 ROM 은 Shift-JIS 2바이트 자리에 한글을 넣었다: 한글 음절은 0x889F 부터 차례로(둘째 바이트 0x40~0x7E, 0x80~0xFC),
  음절 모음은 KS X 1001 + 몇 글자를 가나다순으로 놓은 것(예외 둘: 0x8BB2·0x944E 자리는 순서와 다르다 — 대사 문맥으로 확인).
  0x8740~0x8743 은 받침에 따라 고르는 조사(은/는·이/가·을/를·과/와), 0x889F 아래는 Shift-JIS 기호·전각 영숫자, 1바이트 0x20~0x7E 는 ASCII.
- 정하는 법: 참고 번역 대사와 ROM 대사를 제어 토큰 기준으로 맞춰 같은 길이 조각의 글자끼리 투표(1,198자), 대사에 안 나오는 52자는
  실기 이름 입력칸 글자 그림 + 문맥 + 가나다 이웃으로 읽었다(로컬 파일로 넘긴다). 결과·표는 ROM 에서 나온 것이라 저장소에 넣지 않는다.
- 검증: 2년 진행에서 보여 준 대사·결과 문구에 글자표에 없는 코드 0 (번역 안 된 일본어 장은 위처럼 뺀다).

## 앱 연결 (Core/Orig/OrigSession.cs, Game/GameApp.cs)
- 로컬 원작 팩이 있으면 "처음부터 → 네, 알겠습니다!" 가 원작 코드 진행(신님이 추천하는 가족)으로 시작한다. 없으면 이전 방식(팩 규칙).
  팩 위치: `persistentDataPath/orig/` (orig_rules.json · orig_rules.json.trees · orig_text.json) 또는
  `Resources/LocalOrig/` (orig_rules.json · orig_trees.bytes · orig_text.json). 둘 다 git 에서 제외 — 원작 데이터·번역 대사라 배포 불가.
  - orig_rules.json(+트리): `tools/romlift/export_orig.py` (사용자 ROM). orig_text.json: `tools/romlift/export_text.py`
    (ROM + 참고 자료 events-ko.json · event-scripts-ko.json · planned-states.json). 결과 기록 5,312개 · 관심사 제목 1,108/1,109 개를 맞췄다.
    그다음 `tools/romlift/export_charset.py ROM orig_text.json [손으로_읽은_글자.txt]` 가 글자표를 더한다.
- 원작 메모리가 기준이고 화면용 가족은 매일 원작 레코드에서 다시 만든다(생일·성별·능력치·게이지·몰입도·직업·관심사·화살 표시·족보 관계·가장).
  화살·아이템은 원작 함수로 쓴다(위 "화살·아이템"). 시작 화살은 힘내라·진정해 각 5개(원작 큐피트 튜토리얼 — 튜토리얼 화면은 옮기지 않음).
- 사건은 원작처럼 그날 처리 안에서 효과까지 끝나고, 화면은 뒤이어 대사를 보여 준다. 대사 제어 토큰 중 줄바꿈(1A 01)·글상자 끝(1A 02)·
  대기(1A 09)·이름 자리(1A 06 aa, aa = 장면 슬롯표 칸, 0x27 = 가문)를 쓰고 나머지 연출 토큰은 뺀다. 이름 자리 뜻은 대사 문맥으로 추정.
- 저장: 세이브 영역(0x0202C010~0x0203C440) + 난수 seed + "장면이 날을 끝냄" 을 저장 파일 family.orig.mem(base64)에 넣는다.
  시험: 2년 진행(사건 266개, 모두 대사 있음) 뒤 저장·불러오기 → 60일 같은 사건 106개 · 원작 메모리 같음.
- 아직 원작대로 못 한 것(화면에 영향): 인물 이름(원작 이름 글자표 미해독 — 앱이 붙인 한국어 이름, 상세창에서 바꿀 수 있게 할 예정),
  시작 난수(씨앗 공식은 원작대로, 타이틀 화면에서 돈 횟수만 프레임 수로 대신). 결과 예고·무드·자산·하트·내가 아는 가족은 이식했다.
- Unity 실행은 이 환경에서 확인하지 못했다. `tools/UnityStubCheck` 로 앱 스크립트가 컴파일되는지만 확인한다(UnityEngine 빈 껍데기).

## 아직 해독하지 못한 것 (원작과 다를 수 있음 — 게임에 표시)
원작 세션(OrigSession)의 하루 진행·사건 선택·효과·가족 만들기·화살·아이템은 원작 코드(변환 트리)로 돈다. 남은 것:
1. **아직 옮기지 않은 도구**: 통신 결혼의 화살(통신). 선대의 마음 목록의 스킬 이름은 앱에 아직 없다(번호로 보인다).
2. **결과 문구**: 원작 글 그대로 보인다(글자표가 있을 때). 번역 패치가 옮기지 않은 랭크 보상 설명만 "[앱 요약]"으로 대신한다.
   플레이어 이름 입력 화면이 없어 "신님"으로 보인다. 가문이 끊긴 장면의 화면("N년 가족" 정리·가문의 기록 보기)은 옮기지 않았다.
3. **시작 난수의 타이틀 부분**: 씨앗 공식(VCOUNT×0xAD)은 원작대로, 인트로·타이틀이 돌리는 횟수는 머문 프레임 수로 대신.
4. **화면 표시**: 사건 연출(애니메이션·표정 토큰), 참고 대사의 이름 자리 중 뜻을 모르는 것(→ "○○"),
   큐피트 힌트(`0x0804DB50`).
5. **이름**: 원작 이름 대신 한국식 이름(사용자 결정 — 글자표로 원작 이름을 읽을 수는 있다).
6. 옛 경로(GameSession, 원작 팩이 없을 때)는 공략 데이터 규칙이라 원작과 다르다(몰입도·상태 보정, 사건 빈도 등).
